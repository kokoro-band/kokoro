# 백엔드

Java 17과 Spring Boot 4.1.1을 사용하는 리모델링 프로젝트 API입니다.

먼저 PostgreSQL을 실행합니다. Docker Desktop 또는 호환 런타임이 필요합니다.

```bash
docker compose up -d
./mvnw spring-boot:run
```

기본 포트는 `8080`입니다. 프로젝트와 가구 배치는 PostgreSQL에 저장됩니다. 연결 정보는 `DB_URL`, `DB_USERNAME`, `DB_PASSWORD` 환경 변수로 변경할 수 있습니다. Flyway가 애플리케이션 시작 시 스키마를 적용합니다. 도면 업로드는 형식과 용량을 확인하지만 실제 도면 분석은 아직 실행하지 않습니다.

도면 원본은 로컬 파일에 저장하고 비동기 데모 작업이 PostgreSQL의 상태를 갱신합니다. 실제 도면 인식은 수행하지 않습니다. 저장 경로는 `FLOOR_PLAN_STORAGE_ROOT` 환경 변수로 변경할 수 있습니다. 기본값은 시스템 임시 디렉터리이므로 원본을 보존하려면 별도 영구 경로를 지정해야 합니다. AWS S3 연결과 재시작 후 작업 복구는 후속 작업입니다.

로컬 실행은 `local` 프로파일을 사용해 별도 인증 키 없이 `local-user` 소유자로 동작합니다. 운영에서는 `prod` 프로파일과 `COGNITO_ISSUER_URI`를 사용해 Cognito JWT를 검증합니다.

```bash
./mvnw test
./mvnw package
```

테스트는 운영 데이터베이스와 같은 PostgreSQL 컨테이너를 Testcontainers로 실행합니다. Docker 데몬이 실행 중이어야 하며, 컨테이너 이미지는 테스트 실행 시 자동으로 준비됩니다.

```bash
docker compose down
```

API 요청과 응답은 [API 계약](../docs/contracts/api.md)에 있습니다. 권한 검사와 파일 정리의 남은 작업은 #54와 #12에서 확인합니다. `local`은 개발용 공통 계정이므로 외부 사용자를 위한 운영 인증을 대신하지 않습니다.

## 실행 오류 확인

DB 연결 오류가 나면 `docker compose ps`로 PostgreSQL 상태와 `DB_URL`을 확인합니다. 테스트가 Docker를 찾지 못하면 데몬 실행 여부를 확인합니다. 파일 저장 오류는 `FLOOR_PLAN_STORAGE_ROOT` 경로의 쓰기 권한과 공간을 확인합니다. 운영 프로파일은 `COGNITO_ISSUER_URI`를 설정해야 하며 사용자 로그인 화면은 별도 작업입니다.

## 의존성 보안 검사

`pom.xml`은 Tomcat을 11.0.26으로 관리합니다. Spring Boot가 정하는 core와 el 및 websocket 버전을 함께 바꿉니다. Testcontainers가 테스트에서만 사용하는 Commons Compress는 1.28.0으로 관리하며 실행 API에 직접 추가하지 않습니다. 선택 근거와 재감사 범위는 [의존성 감사 기록](../docs/qa/dependency-audit-2026-09-29.md)에 있습니다.

```bash
./mvnw -Dtest=DependencySecurityTest,TestcontainersArchiveCompatibilityTest test
```

첫 검사는 실제 로드된 라이브러리가 감사한 버전보다 낮아지거나 Tomcat 구성 요소의 버전이 달라지는 것을 막습니다. 두 번째 검사는 실제 컨테이너에 파일을 복사하고 돌려받아 압축 라이브러리 호환성을 확인합니다. Docker가 필요하며 전체 테스트에서도 실행됩니다. 미래의 취약점을 찾는 검사는 아니므로 의존성을 바꿀 때 공개 보안 공지와 감사 결과를 다시 확인합니다.

Spring Boot나 Testcontainers를 올릴 때는 버전을 정하는 기본 목록을 확인합니다. 이 목록을 BOM이라고 합니다. 기본 목록과 전이 의존성이 검증한 수정 버전을 제공하면 해당 버전 재정의를 제거하고 위 검사와 전체 테스트 및 실행 JAR을 다시 확인합니다. 라이브러리의 주요 버전 계열을 바꾸면 회귀 검사의 허용 계열도 근거를 남기고 갱신합니다.

## 회전각 마이그레이션

`V8__preserve_fractional_rotation.sql`은 가구 회전 컬럼을 `INTEGER`에서 `DOUBLE PRECISION`으로 바꿉니다. 정수만 저장하던 칸을 소수를 저장할 수 있는 칸으로 바꾸는 작업입니다. 기존 값과 NOT NULL 제약을 유지하며 새 서버는 `Double`과 JDBC `getDouble`로 읽습니다.

`./mvnw -Dtest=FurnitureRotationTest test`는 별도 PostgreSQL 스키마에 V7까지 적용하고 기존 정수 최솟값과 최댓값을 포함한 데이터를 넣은 뒤 V8로 이행합니다. 타입 변경과 기존 값 및 이후 소수 저장을 확인합니다. API 저장과 조회 및 목록과 공간 변경과 자연어 이동도 검사합니다.

운영 이행 전에는 백업과 복원 절차를 확인하고 구버전 서버의 쓰기를 멈춰야 합니다. 컬럼 타입 변경 중 잠금이 발생할 수 있으므로 실제 데이터 크기에서 소요 시간을 측정해야 합니다. 변경 후 이전 서버의 `getInt` 읽기나 INTEGER 스키마로 단순히 되돌리면 소수값이 유실될 수 있습니다. 자동 역방향 마이그레이션은 제공하지 않습니다. 문제가 생기면 소수 지원 서버를 수정하거나 검증한 백업 복원을 선택해야 하며 배포 전 데이터를 임의로 반올림하지 않습니다.

#132에서는 별도 열린 PR #80의 V6를 그대로 합류시키지 않고 최신 저장 흐름에 맞는 V9로 대체합니다. V1부터 V5 및 V7과 V8 다음 V9 순서와 V8 데이터 업그레이드를 검사합니다. 이후 V6를 추가하지 않습니다. V6를 이미 적용한 별도 DB는 지원 범위 밖이며 실제 이력을 확인한 후 별도 이행 계획이 필요합니다. PR #78의 중복 V5 카탈로그도 아직 통합하지 않았습니다.

## 프로젝트 버전 이행

`V9__integrate_project_revision.sql`은 프로젝트 버전과 제안의 기준 버전을 추가합니다. 기존 가구와 소수 회전값은 보존합니다. 이전 미처리 제안은 기준 버전을 알 수 없어 재요청해야 합니다. [프로젝트 버전 계약](../docs/contracts/project-revision.md)에 요청과 충돌 복구 및 검증 범위를 정리했습니다.

구버전 서버는 버전을 증가시키지 않으므로 신버전과 쓰기 가능한 상태로 혼합 운영하면 안 됩니다. 백업과 복원 절차를 확인하고 모든 구버전 쓰기 경로를 멈춘 뒤 이행합니다. 운영 데이터의 잠금 시간을 미리 측정해야 합니다. 단순히 구버전 서버로 되돌리는 방식은 안전한 롤백이 아니며 자동 역방향 이행은 제공하지 않습니다.
