# 시스템 구조

## 프로젝트 경계

### frontend

React 애플리케이션이 프로젝트 편집 흐름과 2D 도면 보기와 Three.js 3D 장면과 WebXR VR을 모두 담당합니다. 별도 VR 애플리케이션은 만들지 않습니다. 기본 로컬 데모에서는 브라우저 저장소를 사용합니다. `VITE_API_MODE=server`를 설정하면 Spring API를 프로젝트 상태의 최종 소유자로 사용합니다.

### backend

Spring Boot 애플리케이션이 프로젝트 생성과 도면 업로드와 배치 저장과 자연어 명령 처리를 담당합니다. 현재 저장소는 PostgreSQL이며 JDBC로 읽고 씁니다. Flyway가 DB 구조 변경을 관리합니다. 자연어는 규칙 처리기를 사용합니다. 도면 파일은 서버 로컬 디스크에 저장하고 Executor가 데모 작업을 처리합니다. Executor는 프로세스 안에서 작업을 실행하므로 재시작 후 작업 복구는 #4에서 보완해야 합니다.

## 데이터 흐름

```text
전용면적으로 공간 만들기 또는 브라우저에서 도면 이미지 초안 분석
    ↓
사용자가 방과 문과 창을 보정하고 RoomModel 생성
    ↓
프론트엔드가 모델과 가구 배치를 Three.js로 렌더링
    ↓
챗봇 명령 또는 직접 조작으로 Furniture 배열 변경
    ↓
Spring API가 배치 저장
    ↓
같은 웹의 WebXR 세션이 배치를 실제 시점으로 표시
```

## 상태 소유권

| 상태 | MVP 소유자 | 운영 목표 |
|---|---|---|
| 프로젝트와 공간 | 서버 모드 PostgreSQL 또는 로컬 데모 브라우저 저장소 | 요청 순서와 검증 보완 |
| 서버에 업로드한 원본 도면 | 서버 로컬 파일 시스템 | 객체 저장소와 삭제 정책 |
| 서버 도면 작업 상태 | PostgreSQL과 프로세스 내 데모 작업자 | 재시작 복구와 실제 변환 작업자 |
| 브라우저 이미지 분석 초안 | 프론트 편집 상태 | 사용자 확인 후 공간 JSON 저장 |
| 3D 방과 가구 | RoomModel 기반 Three.js 장면과 GLB | 공통 규격과 실제 기기 검증 |
| 가구 배치 | 서버 모드 PostgreSQL 또는 로컬 데모 브라우저 저장소 | 저장 실패와 경합 복구 |
| 편집 중 카메라 | frontend | 저장하지 않음 |
| VR 렌더링 상태 | frontend WebXR 세션 | 저장하지 않음 |

## 운영 전 필수 작업

서버 업로드는 작업 식별자를 반환하고 별도 작업자가 상태를 갱신합니다. 이 작업자는 현재 도면을 분석하지 않으며 잠시 대기한 뒤 READY로 표시합니다. 브라우저의 PlanImport는 이미지 픽셀을 분석해 초안을 만드는 별도 경로입니다. 두 결과를 합쳐 완전 자동 변환이라고 설명하지 않습니다.

운영 전에는 파일 삭제 실패의 재시도와 보존 정책 #12를 해결해야 합니다. 실제 도면 변환기를 붙일 때도 웹 요청에서 오래 실행하지 않고 작업 상태 API를 사용합니다. 자연어 명령은 서버가 대상과 배치를 검증한 뒤 적용하며 확인 절차는 #9와 #60에서 완성합니다.
