# 리모델링 API 계약

기본 주소는 `http://localhost:8080/api`입니다.

로컬 실행은 기본적으로 `local` 프로파일을 사용하며 별도 인증 키 없이 `local-user`를 현재 사용자로 사용합니다. 운영 프로파일은 Cognito JWT를 검증하고 프로젝트 소유자만 프로젝트를 조회·수정·삭제할 수 있습니다.

프로젝트와 가구 배치는 PostgreSQL에 저장되며, 서버 재시작 후에도 같은 프로젝트 ID로 조회할 수 있습니다. 스키마 변경은 Flyway 마이그레이션으로 적용합니다.

## 상태 확인

`GET /health`

## 프로젝트

`GET /projects`는 프로젝트 목록을 반환합니다.

`GET /projects/{projectId}`는 방 치수와 도면과 가구 배치를 포함한 프로젝트를 반환합니다.

`POST /projects`는 프로젝트를 만듭니다.

`DELETE /projects/{projectId}`는 소유자의 프로젝트와 연결된 배치·도면 작업·원본 도면을 삭제합니다.

```json
{
  "name": "우리 집 거실",
  "roomType": "거실",
  "dimensions": { "width": 5.8, "depth": 4.2, "height": 2.4 }
}
```

## 브라우저 로컬 저장 경계

이 절은 server 모드의 HTTP 검증이 아니라 local 데모의 `kokoro-remodel-project-v1` 저장값에 적용됩니다. 브라우저 저장소는 사용자가 수정하거나 손상될 수 있으므로 JSON 파싱 후 실제 필드의 타입과 범위를 다시 검사합니다. 같은 검사를 저장 직전에도 적용하여 저장한 내용을 다음 실행에서 읽지 못하는 일을 막습니다.

| 항목 | 로컬 읽기와 저장 조건 |
|---|---|
| 원본 JSON | 파싱 전에 최대 1,048,576 UTF-16 코드 단위로 제한합니다. 이 수치는 업로드 파일 용량 제한이 아닙니다 |
| 프로젝트 ID | 영문과 숫자 및 `_`와 `-`를 사용한 1~64자 |
| 프로젝트 이름 | 공백만 있는 이름은 거부하고 사용자가 보는 문자 단위로 최대 80자를 허용합니다. 이모지 조합도 한 글자로 셉니다. 새 프로젝트 UI의 60자 제한과 호환됩니다 |
| 기본 치수 | 가로와 세로는 0.5~200m이고 높이는 0.5~20m입니다 |
| 가구 | 최대 200개입니다. ID 중복과 잘못된 분류를 거부합니다. 좌표와 회전은 유한 수치이며 절댓값이 JavaScript의 안전한 정수 상한 이하여야 합니다 |
| 가구 표시 필드 | 이름은 최대 256자이고 색 문자열은 최대 64자입니다. 비어 있는 필드는 거부합니다 |
| 가구와 벽 및 문창의 ID | 최대 128자입니다. 비어 있는 값과 객체의 예약 속성 이름은 거부합니다. 카탈로그 ID도 같은 문자열 검사를 사용합니다 |
| 공간 | 버전 2와 미터 단위를 사용합니다. 벽과 문창은 각각 최대 1024개이고 방 영역은 최대 128개입니다 |
| 다각형 | 각각 3~512점입니다. 방 영역의 좌표 총합은 4096점 이하입니다. 점은 두 유한 수치로 구성하며 공간 범위 안에 있어야 합니다. 넓이가 0이거나 인접한 점이 같은 형태는 거부합니다 |
| 벽과 문창 | 벽의 두 점은 달라야 합니다. 두께는 양수이며 최대 200m입니다. 문창은 존재하는 벽을 참조해야 하며 폭과 높이 구간이 벽 범위에 있어야 합니다 |
| 도면 정보 | 상태 열거값과 0~100 진행률 및 0 이상의 정수 크기를 검사합니다. 파일명은 최대 255자이고 업로드 시각은 유효한 날짜 또는 null입니다 |

가구가 벽 밖에 있거나 현재 카탈로그에 없는 ID를 갖는 것은 손상으로 판정하지 않습니다. 이런 가구는 기존 배치 수정 기능과 대체 모델 표시를 사용합니다. 전체 다각형 교차와 공간 배치 충돌 검사는 이 읽기 검증의 완료 범위가 아닙니다.

방이 없는 신규 프로젝트는 정상입니다. 이전 저장값의 `room: null`은 방 없음으로 처리합니다. 공간의 `rooms: null` 또는 누락된 방 목록은 빈 배열로 처리하고 선택 필드인 `source`와 `spawn`의 null은 생략합니다. 원본 객체는 변경하지 않습니다.

키가 없는 경우는 최초 사용으로 처리합니다. 빈 문자열이나 파싱 실패 또는 형식 오류는 원본을 보존한 채 예제를 표시하고 안내합니다. 저장소 접근이 거부된 경우에는 데이터 손상으로 단정하지 않고 권한 확인을 안내합니다. 읽기와 최초 마운트는 저장값을 삭제하거나 덮어쓰지 않습니다. 이후 사용자가 편집해 저장하면 그 편집 결과로 교체됩니다.

저장 공간 부족과 쓰기 거부에서는 화면 초안을 유지하고 다시 저장할 수 있습니다. 새 로컬 프로젝트도 첫 저장이 성공하기 전까지는 저장되지 않은 상태로 표시하고 이탈 경고를 유지합니다. server 모드는 로컬 프로젝트 JSON을 초기 화면에 사용하지 않습니다. 활성 서버 ID가 잘못되면 요청 전에 오류를 표시하며 다른 프로젝트 ID로 바꾸어 조회하지 않습니다.

#22의 서버 입력 제한과 API 주소 검증은 별도 후속 범위입니다. 서버 도면 업로드와 브라우저 이미지 검증은 아래 절을 따릅니다. 이 절의 로컬 검사가 서버 보안을 대신하지 않습니다.

## 도면

`POST /projects/{projectId}/floor-plan`에 `file`이라는 이름으로 multipart 파일을 전송합니다. multipart는 파일과 파일의 이름 같은 부가 정보를 함께 보내는 요청 형식입니다.

### 서버 원본 도면의 업로드 제한

| 항목 | 허용 범위 |
|---|---|
| 확장자와 선언 MIME | `.pdf`는 `application/pdf`. `.png`는 `image/png`. `.jpg`와 `.jpeg`는 `image/jpeg` |
| 실제 파일 형식 | 확장자와 MIME에 맞는 파일 시작 부분의 고유 바이트를 확인합니다. 이를 시그니처 검사라고 합니다. |
| 파일 크기 | 1바이트 이상 15MiB 이하. 15MiB는 15,728,640바이트입니다. |
| 전체 요청 크기 | 16MiB 이하. 파일 한도와 별도로 multipart의 부가 정보를 위한 여유를 둡니다. |
| 원래 파일명 | 1~255 Unicode 코드 포인트. 한글 음절 하나는 1자로 셉니다. 경로 구분 문자와 제어 문자 및 공백만 있는 이름은 거부합니다. |
| PNG와 JPEG 이미지 크기 | 양수인 가로와 세로의 곱이 16,000,000픽셀 이하 |

확장자와 MIME의 대소문자는 구분하지 않습니다. 파일을 실제로 읽은 길이도 검사합니다. 검증한 바이트를 그대로 저장하므로 검증 이후 원래 스트림을 다시 읽지 않습니다. 원래 파일명은 표시 정보로만 저장하며 파일 경로에는 사용하지 않습니다.

내장 Tomcat은 거부한 요청의 남은 본문을 최대 17MiB까지 버립니다. 한도 근처의 요청에서도 연결이 먼저 끊겨 413 안내가 사라지지 않도록 하기 위한 설정입니다. 무제한으로 본문을 읽지는 않습니다. 훨씬 큰 요청은 서버나 운영 프록시에서 연결 자체를 종료할 수 있습니다.

이미지 크기는 픽셀 데이터를 메모리에 펼치기 전에 헤더에서 읽습니다. 이 검사는 이미지 전체를 끝까지 디코딩하거나 PDF 내부 구조를 해석하지 않습니다. 따라서 시그니처와 크기 검사를 통과했다고 문서 전체가 정상이라는 뜻은 아닙니다. 악성코드 검사도 아닙니다. 향후 실제 변환기를 연결할 때는 변환기의 메모리와 실행 시간 및 PDF 페이지 수 제한을 별도로 적용해야 합니다.

| 응답 | 사용자에게 안내할 내용 |
|---|---|
| 400 | 빈 파일이거나 파일명이 잘못되었습니다. |
| 413 | 파일 또는 전체 요청이 너무 크거나 이미지 픽셀 수가 한도를 초과했습니다. |
| 415 | 지원하지 않는 형식이거나 확장자와 MIME 및 시그니처가 다릅니다. 이미지 크기를 읽을 수 없는 손상된 헤더도 포함합니다. |
| 500 | 읽기나 저장에 실패했습니다. `detail`에 내부 경로나 원래 예외 내용은 포함하지 않습니다. |

거부된 업로드는 프로젝트와 분석 작업을 변경하지 않습니다. 저장 중 오류가 나면 일부만 기록된 파일을 삭제합니다. 운영 파일 시스템 자체가 삭제를 거부하는 경우의 잔여 파일 정리는 #12의 운영 보존 정책 범위입니다. 애플리케이션 검증은 프로젝트 소유권을 확인한 뒤 실행합니다. 서버의 multipart 용량 제한은 소유권 확인 전에도 요청을 거부할 수 있습니다.

이 계약은 서버에 원본 파일을 첨부하는 경로에 적용합니다. 프론트의 공통 HTTP 처리기는 413과 415를 자동 재시도하지 않고 서버의 `detail`을 표시합니다.

### 브라우저 도면 이미지 가져오기

이 경로는 파일을 서버로 보내지 않고 브라우저에서 방 배치 초안을 만듭니다. PNG와 JPEG 및 WebP 정지 이미지만 지원하며 PDF는 지원하지 않습니다. 확장자와 MIME 및 실제 파일 시작 바이트가 일치해야 합니다. PNG의 첫 IHDR와 JPEG의 프레임 헤더 및 WebP의 캔버스와 이미지 헤더에서 크기를 확인합니다. WebP의 두 크기가 서로 다른 경우도 거부합니다.

최대 파일 크기는 15MiB입니다. 픽셀을 메모리에 펼치는 디코딩을 시작하기 전에 양수인 가로와 세로의 곱이 16,000,000 이하인지 확인합니다. 검사를 통과한 뒤에만 이미지 URL과 디코더를 만듭니다. 디코딩 후에는 긴 변을 1200px 이하로 줄여 방을 찾습니다. 이 픽셀 상한은 모든 브라우저에서 정확히 같은 메모리 사용량을 보장하는 값은 아닙니다.

APNG와 애니메이션 WebP는 프레임이 여러 개여서 정지 이미지와 다른 자원 제한이 필요합니다. 현재는 거부하고 정지 이미지로 저장하도록 안내합니다. 파일 구조를 따라 검사하는 단위는 4096개까지 허용합니다. 이를 넘는 특이한 파일은 다시 내보낸 이미지를 사용해야 합니다. 잘린 구조와 중복 크기 헤더도 거부합니다. 이 검사는 이미지 전체의 무결성이나 악성코드를 검사하지 않으며 헤더 이후의 디코딩 실패는 기존 재선택 안내로 처리합니다.

새 파일의 사전 검사가 실패하면 기존 미리보기와 자른 영역 및 적용 가능한 결과를 보존합니다. 진행 중인 기존 분석도 유지합니다. 새 파일 선택은 이전 사전 읽기를 취소하며 이미 완료된 읽기의 늦은 응답도 무시합니다. 닫기와 화면 제거는 읽기와 디코딩 및 분석을 정리합니다. 아직 완료되지 않은 이전 디코딩은 새 파일을 선택했을 때 분석을 시작하지 못하게 합니다.

헤더 위치와 형식은 [PNG 표준](https://www.w3.org/TR/png-3/)과 [JPEG T.81](https://www.w3.org/Graphics/JPEG/itu-t81.pdf) 및 [WebP 컨테이너 명세](https://developers.google.com/speed/webp/docs/riff_container)를 기준으로 했습니다. WebP의 압축 방식별 치수는 [VP8 규격](https://datatracker.ietf.org/doc/html/rfc6386#section-9.1)과 [WebP 무손실 형식](https://developers.google.com/speed/webp/docs/webp_lossless_bitstream_specification)에 정의되어 있습니다.

업로드 응답은 기존 프로젝트 형식을 유지하면서 `floorPlan.jobId`를 함께 반환합니다. 업로드 직후에는 `PROCESSING` 상태이며, 변환 작업은 로컬 저장소 기반 비동기 데모 프로세서가 처리합니다.

도면 이미지를 자동으로 인식하지는 않습니다. 사용자가 평수와 방 개수로 방을 만들고 문과 창을 추가하며, 그 결과는 아래 공간 데이터 API로 저장합니다.

`GET /projects/{projectId}/floor-plan/jobs/{jobId}`로 변환 상태를 조회합니다.

```json
{
  "jobId": "…",
  "projectId": "…",
  "status": "PROCESSING",
  "progress": 25,
  "errorCode": null,
  "errorMessage": null,
  "retryable": true
}
```

완료 상태는 `READY`, 실패 상태는 `FAILED`이며 실패 시 `errorCode`, `errorMessage`, `retryable`을 확인합니다. 현재 저장소 구현은 로컬 파일 시스템이고, 운영 object storage는 `FloorPlanStorage` 구현체를 교체하는 방식으로 연결합니다.

원본 파일의 저장 경로인 `objectKey`는 API 응답에 포함하지 않습니다. 현재 서버의 READY는 데모 작업 상태이며 자동 인식된 공간을 의미하지 않습니다. 브라우저에서 이미지 초안을 만든 뒤 사용자가 보정한 공간은 별도의 공간 저장 API로 전송합니다.

처리 중인 도면이 있는 프로젝트에 새 도면을 업로드하면 `409 Conflict`를 반환합니다. 기존 작업이 완료되거나 실패한 뒤 새 도면을 업로드할 수 있습니다.

서버가 재시작되면 완료되지 않은 작업은 `FAILED`와 `PROCESSING_INTERRUPTED`로 정리되며 다시 업로드할 수 있습니다. 동시에 업로드한 요청은 서버가 한 건만 원자적으로 시작하고 나머지는 `409 Conflict`로 거부하며, 거부된 요청이 임시 저장한 파일은 정리합니다. 도면 처리 상태 갱신은 방과 가구 배치를 덮어쓰지 않습니다.

## 공간 데이터

`PUT /projects/{projectId}/room`

```json
{ "room": { "version": 2, "unit": "m", "wallHeight": 2.4, "bounds": { "width": 10.4, "depth": 6.4 }, "outline": [], "walls": [], "openings": [] } }
```

`room` 본문 형식은 `docs/contracts/room-model.md`를 따릅니다. 저장하면 프로젝트 응답의 `room` 필드로 함께 내려갑니다. 유효한 공간은 기존 가구의 위치와 관계없이 저장합니다. 기존 가구는 자동으로 옮기거나 삭제하지 않습니다. 새 프로젝트의 가구 목록은 비어 있습니다.

## 배치 저장

공간 구조가 유효하지 않으면 `400`과 `code: INVALID_ROOM`을 반환합니다. `violations` 배열의 `path`는 수정할 필드이며 `reason`은 사용자용 이유입니다. 예를 들어 없는 벽을 참조한 문은 `openings[0].wallId`를 가리킵니다. JSON 자체가 잘못되었거나 필수 값이 없으면 표준 요청 검증의 `400`이 반환될 수 있습니다. 어느 경우에도 이전 공간과 배치를 변경하지 않습니다.

`PUT /projects/{projectId}/layout`

```json
{
  "furniture": [
    {
      "id": "sofa-01",
      "catalogId": "sofa-cloud",
      "name": "클라우드 소파",
      "category": "소파",
      "x": 2.4,
      "z": 4.6,
      "rotation": 0,
      "color": "#D8C8B8"
    }
  ]
}
```

`x`와 `z`는 미터이며 원점은 공간 데이터 바운딩 박스의 왼쪽 위입니다. 자세한 규칙은 `docs/contracts/room-model.md`에 있습니다.

수동 배치 저장은 수정 중인 상태도 허용합니다. 집 경계를 벗어나거나 벽과 문 앞 여유 공간을 막거나 가구끼리 겹쳐 있어도 `200`으로 저장합니다. 저장 성공은 배치가 적합하다는 뜻이 아닙니다. 프론트엔드는 현재 공간과 가구 규격으로 위치 문제를 계산하여 `배치 확인 필요` 목록과 선택한 가구의 상세 안내에 표시합니다. 방 밖 가구도 목록에서 선택할 수 있습니다. 하나씩 수정하거나 삭제한 결과는 다른 가구의 문제가 남아 있어도 저장합니다. 새로고침 후에도 저장된 값으로 다시 검사합니다.

지원하지 않는 `catalogId`와 중복된 가구 `id` 및 유한하지 않은 좌표는 계속 `400 Bad Request`로 거절합니다. 필수 필드와 소유권 검증도 유지합니다. 수동 저장에 위치 오류를 허용한다고 해서 잘못된 데이터나 권한 없는 요청을 허용하지는 않습니다.

AI 명령은 기존의 엄격한 배치 검증을 유지합니다. 카탈로그의 폭과 깊이 및 회전값으로 가구의 바닥 사각형을 검사합니다. 공간 데이터가 없으면 `dimensions` 크기의 직사각형을 사용합니다. 경계선에 정확히 닿는 배치는 허용합니다. 경계와 벽과 문 여유 구역 및 가구 겹침 검사에 실패하면 전체 명령을 적용하지 않고 아래 오류를 반환합니다. 수동 배치에 문제가 남아 있으면 AI 명령도 거절될 수 있으므로 배치 확인 목록에서 먼저 수정합니다.

```json
{
  "status": 400,
  "code": "WALL_COLLISION",
  "detail": "가구 '소파'가 벽을 가로지릅니다.",
  "furnitureIds": ["sofa-01"],
  "wallId": "wall-1"
}
```

`code`는 `OUTSIDE_ROOM`, `WALL_COLLISION`, `DOOR_CLEARANCE`, `FURNITURE_OVERLAP` 중 하나이며, 대상은 `furnitureIds`로, 충돌한 벽이나 문은 각각 `wallId`/`openingId`로 식별합니다. 문 여유 구역은 문 구간의 양쪽으로 0.8m를 비워두는 제품 휴리스틱이며 보행이나 시공 기준을 인증하는 수치가 아닙니다.

## 프로젝트 입력 길이와 가구 수

#122의 입력 제한은 다음과 같습니다. UTF-16 단위는 JavaScript의 `string.length`와 Java의 `String.length()`가 세는 길이입니다. 한글은 보통 한 단위이지만 이모지는 두 단위 이상일 수 있습니다. grapheme은 화면에서 한 글자로 보이는 묶음입니다.

| 입력 | 브라우저 정책 | 서버 쓰기 정책 |
|---|---|---|
| 프로젝트 이름 | 공백뿐인 값은 거부합니다. 최대 80 grapheme이며 원문은 1024 UTF-16 단위 이하입니다. | 공백뿐인 값은 거부합니다. 원문은 1024 UTF-16 단위 이하입니다. |
| 방 종류 | 로컬 저장에서 공백뿐인 값과 80 UTF-16 단위 초과를 거부합니다. 생성 화면은 정해진 방 종류를 보냅니다. | 공백뿐인 값과 80 UTF-16 단위 초과를 거부합니다. |
| 배치 요청 | 공백뿐인 값과 1000 UTF-16 단위 초과를 전송 전에 거부합니다. | 같은 범위로 검사한 뒤 명령을 해석합니다. |
| 가구 목록 | 저장과 로컬 명령 결과가 200개를 넘으면 거부합니다. | 수동 저장과 명령 적용 모두 기하 계산 전에 200개 상한을 검사합니다. |

브라우저와 Java 17은 사용하는 Unicode 버전이 달라 grapheme을 항상 같은 수로 세지 않습니다. 서버가 UI보다 더 엄격하게 유효한 이름을 거절하지 않도록 이름의 80글자 정책은 브라우저에 두고 서버는 원문 안전 상한만 검사합니다. 따라서 서버 직접 호출로 81글자 이름을 저장하는 것은 허용됩니다. 이 차이는 의도한 계약이며 공유 예제 `fixtures/input-boundaries.json`의 `client`와 `server` 값으로 구분합니다. 가족 이모지 80개와 인도 문자 및 긴 결합 문자도 예제에 포함됩니다.

이름 DB 컬럼은 `TEXT`로 확장합니다. 기존 이름을 축약하거나 삭제하지 않습니다. 새 요청만 위 제한으로 검사합니다. 로컬 저장 경계에 맞지 않는 기존 원본은 기존 복구 절차대로 보존합니다. 실패한 채팅 입력은 대화 기록을 추가하거나 입력창을 비우기 전에 안내합니다. 프로젝트 이름 실패도 화면 전환 전에 차단합니다.

서버의 잘못된 값은 한국어 `detail`이 있는 `400` 응답입니다. 제출한 원문이나 내부 예외를 응답에 복사하지 않습니다. 파일 크기의 `413`과 형식의 `415`는 별도 업로드 계약을 따릅니다. 이 입력 검사는 JSON 파싱 전에 전체 요청 크기를 제한하는 기능이 아니며 요청 속도 제한도 아닙니다. 전체 JSON 전송량과 운영 제한은 #10의 후속 검증 범위입니다. 가구 필드와 공간 수치는 아래 #128의 후속 계약을 따릅니다.

## 가구 필드와 공간 수치의 저장 경계

#128은 새 가구 저장 요청이 DB 컬럼에 들어가지 못하거나 브라우저에서 처리할 수 없는 수치로 저장되는 것을 막습니다. 공통 예제는 `fixtures/furniture-input-boundaries.json`입니다. 길이는 모두 UTF-16 단위입니다. DB의 문자 수와 같다고 주장하지 않으며 이모지는 두 단위로 계산해 더 보수적으로 제한합니다.

| 필드 | 새 가구 저장의 허용 범위 |
|---|---|
| `id`와 `catalogId` | 각각 1~100단위입니다. 공백뿐인 값과 NUL 문자는 거부합니다. `__proto__`와 `constructor` 및 `prototype`은 사용할 수 없습니다. 가구 ID는 중복될 수 없습니다. |
| `name` | 공백이 아닌 1~200단위이며 NUL 문자를 거부합니다. |
| `color` | 공백이 아닌 1~20단위이며 NUL 문자를 거부합니다. 이 검사는 색상 표현식의 문법 전체를 검증하는 것은 아닙니다. |
| `category` | 소파 또는 테이블 또는 의자 또는 장식입니다. |
| `x`와 `z` | 유한한 숫자이며 절댓값이 `Number.MAX_SAFE_INTEGER`인 9007199254740991 이하여야 합니다. 방 밖의 유효한 위치도 수동 복구를 위해 저장합니다. |
| 목록과 요소 | null 목록과 null 요소를 거부합니다. 200개 상한은 기존과 같습니다. |

브라우저는 가구 저장 요청 전에 위 검사를 실행하고 실패하면 전송과 로컬 저장을 시작하지 않습니다. 서버는 기하 계산과 DB 쓰기 전에 같은 경계를 검사합니다. 알 수 없는 카탈로그의 서버 저장 거부는 기존 규칙을 유지합니다. 로컬에서는 알 수 없는 카탈로그를 읽고 삭제할 수 있는 기존 복구 방식을 유지하므로 이 부분은 서버와 의도적으로 다릅니다.

기존 로컬 읽기는 가구 ID 128단위와 이름 256단위 및 색상 64단위의 종전 범위를 유지합니다. 새 저장 제한 때문에 전체 프로젝트를 손상 데이터로 취급하지 않습니다. 새 저장이 실패하면 원본 저장소와 화면의 초안은 그대로 둡니다. 기존 한도를 초과하는 가구는 현재 이름 변경 UI가 없으므로 해당 가구를 삭제하고 카탈로그에서 다시 추가해 복구할 수 있습니다. 자동으로 값을 줄이거나 가구를 지우지 않습니다.

프로젝트 생성의 가로와 세로는 0.5~200m이며 높이는 0.5~20m입니다. 서버도 브라우저 로컬 검사와 같은 범위를 적용합니다. 벽 두께는 `Number.EPSILON`인 약 `2.22e-16` 이상이며 200m 이하입니다. 이는 처리 가능한 데이터 경계이며 권장 시공 치수가 아닙니다. 값이 잘못되면 생성은 DB 행을 추가하지 않고 기존 프로젝트의 가구와 공간 저장은 변경 전 상태를 유지합니다.

서버의 공통 문자열 검사는 프로젝트 이름과 방 종류 및 채팅의 NUL 문자도 거부합니다. 해당 프로젝트 및 채팅 필드의 브라우저 사전 검사는 아직 NUL을 별도로 차단하지 않으므로 전체 문자열 정책이 같다고 해석하지 않습니다. NUL은 문자열 중간에 넣을 수 있지만 PostgreSQL 텍스트에는 저장할 수 없는 제어 문자입니다.

회전값의 소수 정밀도는 아래 #129의 계약을 따릅니다. #128 통과가 전체 숫자 계약이나 실제 웹과 Spring 연결 E2E #11 완료를 뜻하지 않습니다.

## 소수 회전각 저장

#129부터 가구 `rotation`은 소수를 포함하는 JSON 숫자입니다. 단위는 도이며 유한한 값이고 절댓값이 9007199254740991 이하여야 합니다. null과 NaN 및 Infinity와 범위 초과 값은 저장 전에 거부합니다. 잘못된 요청은 기존 배치와 갱신 시각을 바꾸지 않습니다.

수동 저장은 회전각을 0~360으로 바꾸거나 정수로 자르지 않습니다. 예를 들어 `4.5`와 `25.25` 및 `-25.25`와 `720.5`는 같은 숫자로 조회됩니다. 벽 앞에서 회전을 멈추는 프론트 보정이 소수 각도를 만들 수 있으므로 서버가 각도를 바꾸면 저장 후 벽을 침범할 수 있습니다. 목록 조회와 공간 변경 및 자연어 이동 명령에서도 기존 회전각을 유지합니다.

Java와 PostgreSQL은 64비트 부동소수점으로 저장하고 읽습니다. 이는 브라우저 숫자와 같은 방식으로 근사한 이진수 값을 사용한다는 뜻입니다. 십진수를 무한히 정확하게 저장하는 계약은 아니며 `0.1`도 같은 입력 숫자로 왕복하는지 검사합니다. 정수 입력은 여전히 허용하며 JSON 출력이 `0` 대신 `0.0`일 수 있으므로 문자열이 아닌 숫자로 해석해야 합니다.

공통 예제는 `fixtures/furniture-rotation.json`입니다. 프론트의 실제 벽 회전 함수가 `4.5`를 반환하는 사례와 저장 및 복원 예제를 포함합니다. 현재 규칙 기반 자연어 해석기의 회전 명령은 기존 정수 문법을 유지합니다. 가구 저장 타입이 소수가 됐다는 이유로 자연어의 소수 각도 해석까지 지원한다고 표현하지 않습니다.

DB 이행과 이전 서버로 되돌릴 때의 제한은 [백엔드 안내](../../backend/README.md)의 회전각 마이그레이션 절을 따릅니다. 실제 전체 편집 흐름의 반복 E2E와 운영 인증은 #11과 #12에서 별도로 검증합니다.

## 클라이언트 API 주소 경계

#124에서 `VITE_API_BASE_URL`을 실제 전송 전에 검증합니다. 개발 모드의 미설정은 기존 `http://localhost:8080/api`를 사용합니다. 배포 빌드에서는 HTTPS API 주소나 `/api` 같은 같은 출처의 경로를 명시해야 합니다. 로컬 데모는 요청을 보내지 않으므로 API 미설정으로 초기 렌더링이 실패하지 않습니다. 서버 모드의 설정 오류는 `status: null`과 `retryable: false`인 `ApiError`로 화면에 전달됩니다.

HTTP 개발 주소는 정확한 loopback 표기만 허용합니다. 자세한 허용값과 배포 설정은 `frontend/README.md`의 API 주소 설정을 따릅니다. Axios 요청별 주소는 `/projects` 같은 루트 상대 API 경로이며 초기 주소의 접두 경로 뒤에 결합합니다. 예를 들어 `https://host/prefix/api`와 `/projects`는 `https://host/prefix/api/projects`가 됩니다. 다른 절대 주소와 `baseURL` 덮어쓰기는 전송 전에 거부합니다. 사용자 입력을 URL 문자열로 직접 붙이지 않고 검증된 프로젝트 ID만 사용합니다.

검증 대상은 최초 요청 주소입니다. 브라우저가 따르는 서버 리디렉션과 DNS 변경 및 서버의 CORS나 인증 설정을 대신하지 않습니다. 잘못된 설정에서 자동 재시도하지 않는다는 것은 사용자가 재시도 버튼을 누를 수 없다는 뜻이 아니라 같은 설정으로 백그라운드 반복 요청을 보내지 않는다는 뜻입니다.

## 자연어 배치

`POST /projects/{projectId}/layout/commands`

```json
{ "message": "창가에 식물과 소파를 배치해줘" }
```

응답은 사용자에게 보여줄 문장과 적용한 동작과 변경된 프로젝트를 함께 반환합니다. 현재 처리기는 소파와 테이블과 의자와 화분과 비우기 명령을 지원합니다.

자연어 명령 응답에는 구조화된 `commands`도 포함됩니다. 명령 타입은 `ADD`, `MOVE`, `ROTATE`, `REMOVE`, `CLEAR`이며, 대상을 찾지 못한 명령이 하나라도 있으면 전체 요청을 `400 Bad Request`로 거부하고 아무것도 적용하지 않습니다.

같은 `catalogId`의 가구가 여러 개면 임의로 하나를 고르지 않고, 응답의 `candidates`(`furnitureId`, `name`)로 후보를 돌려주고 아무것도 바꾸지 않습니다. 요청에 `furnitureId`를 함께 보내면 그 가구를 대상으로 확정합니다:

```json
{ "message": "의자를 90도 회전해줘", "furnitureId": "chair-01" }
```

전체 삭제처럼 되돌리기 어려운 명령은 즉시 적용하지 않고 `requiresConfirmation: true`와 `proposalId`, `expiresAt`(5분 뒤 만료), `proposedCommands`로 확인을 먼저 요청합니다. 이 시점까지 `appliedActions`는 비어 있고 프로젝트는 바뀌지 않습니다.

`POST /projects/{projectId}/layout/commands/confirm`

```json
{ "proposalId": "..." }
```

제안된 명령만 실행하며 임의의 `commands`는 받지 않습니다. `proposalId`가 없거나 다른 사용자의 제안이면 `404`, 만료됐거나 제안 이후 배치가 바뀌었으면(`updatedAt` 불일치) `409`입니다. 같은 `proposalId`를 다시 보내면 재실행 없이 이미 처리된 결과 상태를 그대로 반환합니다.

### 웹 확인 화면

확인 전과 취소 후에는 화면 배치와 실행 취소 이력 및 저장 결과를 바꾸지 않습니다. 전체 삭제는 대상 이름을 먼저 보여 줍니다. 후보가 여러 개면 이름과 좌표를 보여 주고 선택한 `furnitureId`와 원래 요청 문장만 다시 보냅니다. 확인 전 프로젝트를 바꾸거나 배치를 편집하면 기존 제안을 적용할 수 없습니다.

확인 응답이 유실되면 같은 `proposalId`로 다시 확인합니다. 서버가 이미 처리한 제안은 `appliedActions`가 비어 있어도 응답의 현재 프로젝트를 화면에 반영합니다. 결과가 불명확한 재시도는 원래 만료 시간이 지났다는 이유만으로 클라이언트에서 차단하지 않습니다. 서버가 `404` 또는 `409`를 반환하면 새 제안을 요청하도록 안내합니다.

로컬 규칙 데모도 같은 확인 화면을 사용합니다. 로컬 제안은 현재 페이지의 메모리에만 있고 최대 50개를 보관합니다. 새로고침하면 사라지며 서버의 사용자 인증이나 영속 저장을 대신하지 않습니다. 로컬 확인은 브라우저 저장에 성공한 뒤에만 제안을 소비합니다. 소비한 제안을 다시 확인해도 나중에 편집한 배치를 덮지 않습니다.
