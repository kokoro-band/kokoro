# 로컬 모델의 배치 요청 계약

모델은 사용자 문장을 명령으로 해석합니다. 서버는 실제 가구와 공간을 조회해 좌표를 계산합니다. 모델이 만든 코드를 실행하거나 URL을 방문하지 않습니다. 저장은 별도의 확인 요청으로만 수행합니다.

## 미리보기 요청

`POST /api/projects/{projectId}/layout/proposals/intent`를 사용합니다. `expectedRevision`은 요청이 기준으로 삼는 프로젝트 버전입니다. 서버 버전과 다르면 409로 거부합니다.

```json
{
  "expectedRevision": 3,
  "selectedFurnitureId": null,
  "focusRoomName": "거실",
  "choices": {},
  "intent": {
    "reply": "소파 오른쪽에 화분을 제안해요.",
    "commands": [
      {
        "action": "ADD",
        "catalogId": "plant-olive",
        "targetQuery": null,
        "anchorQuery": "소파",
        "placement": "RIGHT",
        "distanceM": 0.3,
        "rotation": 0,
        "count": 1
      }
    ]
  }
}
```

사용하지 않는 명령 필드도 `null`이나 기본값으로 보냅니다. 임의의 필드와 알 수 없는 명령 및 유효하지 않은 숫자는 거부합니다. 명령은 최대 8개입니다. 한 명령에서 추가하는 가구는 최대 5개이며 전체 추가 수는 12개 이하입니다. 프로젝트의 가구 수는 최대 200개입니다.

| 필드 | 뜻 |
|---|---|
| action | ADD는 추가입니다. MOVE는 이동입니다. ROTATE는 절대 각도 변경입니다. REMOVE는 한 가구 삭제입니다. CLEAR는 프로젝트 전체 가구 삭제입니다. |
| catalogId | 추가할 때 사용하는 서버 카탈로그의 ID입니다. |
| targetQuery | 변경할 가구의 이름이나 분류입니다. 선택한 가구라는 표현은 selectedFurnitureId를 사용합니다. |
| anchorQuery | 상대 배치의 기준이 되는 다른 가구입니다. 기준을 요청하지 않았다면 null입니다. |
| placement | 위치나 이동 방향입니다. |
| distanceM | 미터 단위 거리입니다. 0부터 5까지 허용합니다. |
| rotation | -360부터 360까지의 정수 각도입니다. 서버에서 0부터 359로 정규화합니다. |
| count | 추가 수입니다. 이동과 회전 및 개별 삭제에서는 1이어야 합니다. |

`CLEAR`는 다른 명령과 함께 보내지 않습니다. 하나의 제안에 속한 명령은 순서대로 계산하지만 일부만 저장하지 않습니다. 마지막 결과 전체가 검증되어야 제안을 생성합니다.

## 위치 해석

`AUTO`와 `CENTER`는 공간 중심 근처에서 시작합니다. `LEFT`와 `RIGHT` 및 `FRONT`와 `BACK`은 방이나 기준 가구의 방향입니다. X가 증가하는 쪽은 오른쪽이며 Z가 증가하는 쪽은 앞쪽입니다. 카메라를 돌려도 이 기준은 바뀌지 않습니다.

`OFFSET_LEFT`와 같은 표현은 원래 가구 위치에서 지정한 거리만큼 이동합니다. 이 경우 충돌이 나면 다른 거리로 슬쩍 바꾸지 않고 거부합니다. 추가 명령에는 OFFSET을 사용할 수 없습니다.

`NEAR_WINDOW`와 `NEAR_DOOR`는 공간에 실제 등록된 개구부를 사용합니다. 개구부는 벽에 뚫린 문이나 창문을 뜻합니다. 같은 종류가 여럿이면 사용자가 고릅니다. 없는 창문이나 문은 임의로 추정하지 않습니다.

`focusRoomName`이 있으면 그 이름의 방 영역 안에서 후보를 찾습니다. 이름이 중복되면 거부합니다. 방을 지정하지 않으면 집 전체를 사용합니다. 기존 가구의 대상 검색은 프로젝트 전체이며 선택한 방은 새 위치를 제한합니다.

좌표 후보는 0.1m 간격으로 가까운 순서대로 검사합니다. 한 가구당 검사 수는 최대 1200개입니다. 기본 탐색 오프셋은 각 축의 -3m부터 3m까지이며 문과 창문 주변은 2m 이내입니다. 내부 벽과 문 앞 여유 공간 및 다른 가구와 겹치는 후보는 제외합니다. 제한된 탐색이므로 실패했다고 해서 가능한 배치가 전혀 없다는 의미는 아닙니다.

## 사용자가 대상을 골라야 할 때

같은 이름의 가구가 여럿이면 422 응답을 받습니다.

```json
{
  "status": 422,
  "code": "AMBIGUOUS_TARGET",
  "detail": "어떤 가구를 뜻하는지 선택해 주세요.",
  "choiceKey": "0:target",
  "candidates": [
    {"id": "first-chair", "name": "셸 체어 (2.0m, 3.0m)"},
    {"id": "second-chair", "name": "셸 체어 (4.0m, 3.0m)"}
  ]
}
```

프론트는 모델을 다시 호출하지 않습니다. 원래 요청에 `choices: {"0:target": "second-chair"}`를 추가해 같은 API로 보냅니다. 숫자는 명령 순서이며 0부터 시작합니다. `anchor`는 기준 가구나 문과 창문 선택입니다. 후보에 없는 ID는 거부합니다.

같은 요청에서 먼저 추가한 가구도 나중 명령의 대상이 될 수 있습니다. 추가 ID는 프로젝트와 기준 버전 및 명령 내용과 순서로 정해집니다. 따라서 선택을 다시 보내도 ID가 바뀌지 않습니다.

후보가 없는 `NO_TARGET`과 `NO_ANCHOR` 및 `NO_VALID_PLACEMENT`는 새 요청이 필요합니다. 모호한 경우에만 후보 버튼을 보여 줍니다.

## 확인과 복구

성공하면 [명령 제안 계약](layout-proposals.md)의 PENDING 응답을 받습니다. 미리보기 자체는 프로젝트를 저장하지 않습니다. 확인할 때 서버가 다시 검증한 뒤 한 번만 적용합니다.

프론트는 먼저 진행 중인 수동 저장을 마칩니다. 제안을 확인하거나 취소하기 전에는 다른 쓰기를 막습니다. 확인 응답을 잃으면 같은 제안의 상태를 조회합니다. 페이지를 다시 열어 제안을 복구할 때는 제안이 속한 프로젝트를 먼저 불러오며 다른 프로젝트의 공간에 미리보기를 섞지 않습니다.

이미 적용된 제안의 result는 적용 당시 기록입니다. 최신 화면에는 별도 프로젝트 조회 결과를 사용합니다. 오래된 제안과 만료된 제안을 자동으로 다시 생성하거나 확인하지 않습니다.
