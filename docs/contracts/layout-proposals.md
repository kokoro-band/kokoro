# 명령 제안과 확인

제안은 서버가 검증한 예상 배치입니다. 미리보기 생성만으로 프로젝트를 저장하지 않습니다. 사용자가 확인하면 제안에 저장된 배치를 한 번만 적용합니다.

## 구현된 API

기본 경로는 `/api/projects/{projectId}/layout/proposals`입니다.

| 요청 | 용도 |
|---|---|
| POST 기본 경로 | 절대 좌표 명령을 검증하고 제안 생성 |
| POST /intent | 로컬 모델의 의미 명령을 좌표로 계산하고 제안 생성 |
| GET /{proposalId} | 현재 제안 상태와 이미 적용한 결과 조회 |
| POST /{proposalId}/confirm | 저장된 제안을 확인하고 적용 |
| POST /{proposalId}/cancel | 아직 적용하지 않은 제안 취소 |

생성 요청은 `expectedRevision`과 `commands`를 받습니다. 기준 버전은 필수입니다. 명령은 1~8개이며 `ADD`와 `MOVE` 및 `ROTATE`와 `REMOVE`와 `CLEAR`를 지원합니다. `CLEAR`는 단독으로 요청합니다.

```json
{
  "expectedRevision": 0,
  "commands": [
    {"type": "ADD", "catalogId": "chair-shell", "x": 2, "z": 2, "rotation": 0}
  ]
}
```

추가는 서버 카탈로그의 이름과 색상 및 규격을 사용합니다. 이동과 회전 및 개별 삭제는 배치 인스턴스의 `furnitureId`가 필수입니다. 같은 카탈로그의 첫 번째 가구를 임의로 선택하지 않습니다. 위치는 미터이며 회전은 절대 각도입니다.

## 상태와 응답

응답에는 `id`와 `status` 및 `baseRevision`과 `expiresAt`이 있습니다. `proposedFurniture`는 예상 가구 목록이며 `actions`는 사용자가 확인할 변경 설명입니다. `actions`가 있어도 `PENDING`은 저장 완료 상태가 아닙니다.

| status | 뜻 |
|---|---|
| PENDING | 확인 또는 취소 가능 |
| APPLIED | 이미 저장됨. result에 적용 당시 프로젝트가 있음 |
| CANCELLED | 취소됨 |
| EXPIRED | 생성 후 5분이 지나 확인할 수 없음 |
| STALE | 프로젝트가 변경되어 다시 제안해야 함 |

확인 요청에는 새 명령이나 가구 목록을 전달하지 않습니다. URL의 제안 ID에 해당하는 서버 저장 내용만 사용합니다. 확인 시 현재 규격으로 전체 배치를 다시 검증합니다. 하나라도 실패하면 가구 저장과 제안 적용 상태가 모두 취소됩니다.

만료되거나 취소되거나 오래된 제안을 확인하면 409입니다. 없는 제안이나 다른 프로젝트 또는 다른 소유자의 제안은 404입니다. 같은 제안을 다시 확인하면 재실행하지 않고 기존 결과를 반환합니다.

## 응답을 받지 못했을 때

확인 요청 이후 연결이 끊기면 같은 제안의 상태를 먼저 조회합니다. `APPLIED`이면 다시 배치를 생성하지 않습니다. `result`는 최초 적용 당시의 기록이므로 이후 편집된 프로젝트보다 오래될 수 있습니다. 화면 복구에는 프로젝트의 최신 응답을 읽어 사용합니다.

확인 요청부터 상태를 확정할 때까지 프론트는 수동 편집을 잠가야 합니다. 사용자가 확인 대신 취소해도 이미 적용된 요청을 되돌리는 기능은 아닙니다. 취소 응답이 `APPLIED`이면 저장된 상태를 불러옵니다.

## 자연어 연결과 기존 API

서버 모드의 AI 배치 화면은 사용자 PC의 Ollama를 호출한 뒤 `/intent`로 의미 명령을 전달합니다. 상대 위치와 모호한 대상 선택은 [로컬 모델 요청 계약](layout-intents.md)을 따릅니다. 기존 `/layout/commands` 규칙 처리기는 이 제안 API로 전환하지 않았으며 새 AI 화면은 그 경로를 사용하지 않습니다. 브라우저 로컬 데모의 규칙 처리도 실제 모델과 구분합니다.
