# 프로젝트 버전과 저장

`revision`은 프로젝트가 변경된 횟수를 나타내는 서버의 버전 번호입니다. 새 프로젝트는 0에서 시작합니다. 같은 내용으로 다시 저장해도 번호가 증가합니다. 사용자가 내용을 원래대로 돌린 경우에도 이전 AI 제안을 재사용하지 않기 위해 필요합니다.

## 요청과 응답

프로젝트 응답에 `revision`을 포함합니다. 배치 저장과 공간 저장 및 기존 명령 요청은 `expectedRevision`을 받을 수 있습니다. 클라이언트는 편집을 시작한 서버 응답의 번호를 전달합니다.

```json
{"expectedRevision": 3, "furniture": []}
```

서버의 현재 번호가 3이면 저장 후 응답은 4입니다. 다른 요청이 먼저 저장했다면 HTTP 409를 반환하며 아무것도 바꾸지 않습니다. 이때 최신 프로젝트를 읽고 사용자에게 다시 확인받아야 합니다. 번호만 바꾸어 이전 요청을 자동 재전송하면 다른 편집을 덮어쓸 수 있습니다.

기존 웹의 전환 기간에는 `expectedRevision` 생략을 허용합니다. 생략 요청도 잠금과 버전 증가를 거치지만 사용자가 오래된 화면에서 보냈는지 판별할 수 없습니다. 따라서 이것만으로 프론트 저장 안정화가 끝난 것은 아닙니다. 새 AI 제안 API에서는 기준 번호를 필수로 받습니다.

## 서버 처리

서버는 같은 프로젝트의 변경을 DB 행 잠금으로 순서대로 처리합니다. 행 잠금은 한 요청의 저장이 끝날 때까지 다른 요청이 같은 프로젝트를 변경하지 못하게 하는 기능입니다. 조회는 프로젝트 정보와 가구 목록을 동일한 DB 시점으로 읽습니다.

도면 상태 변경도 번호를 증가시킵니다. 현재 도면 작업의 식별자가 일치하고 처리 중인 경우에만 도면 필드를 변경합니다. 가구 목록이나 공간 구조는 다시 저장하지 않습니다. 파일 업로드로 등록한 작업은 DB 저장이 확정된 후 실행합니다.

## 확인한 범위

`ProjectRevisionTest`에서 동시 저장과 이전 번호 거부 및 같은 내용의 재저장과 공간 변경을 검사합니다. 다른 소유자의 변경 거부와 이전 도면 작업 무시 및 도면 갱신 시 가구 보존도 실제 PostgreSQL에서 검사합니다. 업로드 작업을 실행할 때 다른 DB 연결에서도 등록된 작업을 읽을 수 있는지 확인합니다.
