# 프로젝트 버전과 동시 저장

## 사용자가 보호받는 동작

#132는 #79와 PR #80의 버전 보호 기능을 최신 서버 저장 방식에 맞게 다시 연결합니다. 같은 상태를 보고 보낸 두 저장 요청 중 하나가 먼저 완료되면 나머지는 `409 Conflict`로 거절합니다. 실패한 요청은 방과 가구 및 버전과 제안의 처리 여부를 바꾸지 않습니다.

`revision`은 프로젝트가 변경될 때마다 증가하는 정수입니다. 새 프로젝트는 0이며 API의 프로젝트 응답에 포함됩니다. 단건 조회와 목록 조회는 프로젝트와 가구를 같은 시점의 데이터로 읽습니다. 조회 도중 저장이 완료돼도 이전 버전과 새로운 가구 목록을 섞어 반환하지 않습니다.

## 요청 계약

다음 세 경로는 요청 본문에 선택적으로 `expectedRevision`을 받습니다. 이는 사용자가 편집을 시작한 프로젝트의 버전입니다. 음수는 허용하지 않습니다.

| 경로 | 기존 필드 | 추가 필드 |
|---|---|---|
| `PUT /api/projects/{id}/layout` | `furniture` | `expectedRevision` |
| `PUT /api/projects/{id}/room` | `room` | `expectedRevision` |
| `POST /api/projects/{id}/layout/commands` | `message`와 선택적인 `furnitureId` | `expectedRevision` |

```json
{ "furniture": [], "expectedRevision": 3 }
```

현재 서버 버전이 3이면 저장 후 버전 4를 반환합니다. 이미 4라면 요청을 실행하지 않고 409를 반환합니다. 버전을 생략하거나 null로 보내는 기존 클라이언트는 전환 기간에 허용합니다. 이 경우 서로 다른 방과 가구 필드를 서버 내부의 오래된 복사본으로 덮어쓰는 문제는 막지만 두 탭이 같은 가구 목록을 덮어쓰는 문제까지 막지는 않습니다.

방과 가구 저장은 내용이 이전과 같더라도 성공하면 버전이 증가합니다. 자연어 후보 선택과 제안 생성은 프로젝트를 바꾸지 않으므로 증가하지 않습니다. 실제 명령 적용과 도면 업로드 시작 및 처리 상태 변경과 실패 복구는 증가합니다. 삭제된 프로젝트는 다시 생성하지 않습니다.

## 전체 삭제 확인

서버가 제안을 만들 때 당시의 `revision`을 함께 저장합니다. 확인 요청은 기존처럼 `proposalId`만 받습니다. 만료됐거나 현재 버전이 다르면 409입니다. 배치를 바꿨다가 원래대로 돌렸거나 변경 시각이 같아도 이전 제안은 유효해지지 않습니다.

이미 처리된 제안을 다시 확인하면 명령을 재실행하지 않고 현재 프로젝트를 반환합니다. 이 재확인으로 버전이 증가하지 않습니다. 업그레이드 전 생성된 미처리 제안은 기준 버전을 알 수 없으므로 거절하고 새로 요청하도록 합니다.

## 서버 구현 경계

서버는 변경 전에 프로젝트 행을 잠급니다. 행 잠금은 다른 저장이 같은 프로젝트를 동시에 수정하지 못하도록 DB가 잠시 기다리게 하는 기능입니다. 잠근 다음 최신 방과 가구 및 버전을 읽고 요청을 검사합니다. 프로젝트 변경과 가구 교체는 한 트랜잭션으로 처리합니다. 트랜잭션은 중간 실패가 있으면 변경 전체를 취소하는 DB 작업 단위입니다.

잠금 순서는 프로젝트 다음 도면 작업 또는 제안입니다. 도면 상태 갱신은 현재 작업 ID가 일치하고 처리 중인 경우에만 수행합니다. 끝난 작업이나 이전 작업이 새 작업을 되돌릴 수 없습니다. 시작 시 복구는 잠근 프로젝트 목록의 해당 작업만 실패 처리합니다. 목록을 읽은 뒤 다른 프로젝트에서 시작한 새 업로드를 함께 실패 처리하지 않습니다.

과거 데이터에 작업 ID 없이 처리 중인 프로젝트가 있으면 실패 상태로 복구해 다시 업로드할 수 있게 합니다. 프로젝트와 작업 상태가 불일치하더라도 이미 끝난 작업 이력은 바꾸지 않습니다. 이 경우 처리 중으로 남은 프로젝트만 재시도 가능한 실패 상태로 바꿉니다.

## 프론트의 저장과 복구

#133의 프론트는 서버 응답의 버전을 보존하고 방과 가구 저장 및 자연어 명령에 기준 버전을 보냅니다. 누락되거나 음수인 버전과 안전한 정수 범위를 벗어난 값은 거절합니다. 다른 프로젝트 ID나 요청 당시보다 낮은 버전이 반환돼도 화면에 채택하지 않습니다. 로컬 데모는 서버 버전을 만들지 않으며 기존 기기 저장 형식을 유지합니다.

저장 대기열은 요청을 순서대로 실행하는 장치입니다. 다음 요청에는 클릭 당시 버전이 아니라 직전 성공 응답의 버전을 사용합니다. 화면의 편집 초안은 별도로 유지하므로 저장을 기다리는 동안 바꾼 가구를 이전 응답으로 덮어쓰지 않습니다. 도면 상태 조회도 대기열에서 실행합니다. 상태 조회에서 방이나 가구까지 달라졌다면 외부 편집으로 보고 충돌 복구를 안내합니다. 프로젝트 전환 뒤 도착한 이전 응답은 현재 화면에 반영하지 않습니다.

409는 연결 실패와 다르게 취급합니다. 자동 저장을 멈추고 편집 초안과 저장 충돌 해결 버튼을 남깁니다. 최신 버전으로 자동 재전송하지 않습니다. 사용자는 다음 행동을 선택할 수 있습니다.

| 선택 | 화면과 서버의 결과 |
|---|---|
| 최신 내용 확인 | 서버 버전과 방 및 가구 개수만 미리 봅니다. 저장 기준과 내 초안은 그대로입니다. |
| 내 초안 버리고 서버 내용 사용 | 확인창에서 동의하면 미저장 구조와 가구 및 실행 취소 기록을 버리고 확인한 서버 내용을 엽니다. 서버 쓰기는 발생하지 않습니다. |
| 내 변경을 최신 내용에 적용 | 확인한 버전 위에 내 변경을 다시 저장합니다. 그 사이 다른 저장이 있으면 다시 충돌하며 초안을 보존합니다. |
| 나중에 해결 | 안내창만 닫습니다. 저장 중단과 초안 보존은 계속됩니다. |

가구 재적용은 마지막 성공 상태와 현재 초안을 비교합니다. 내가 수정하지 않은 가구에는 서버 내용을 사용하고 직접 바꾼 가구에는 내 가구 전체 내용을 사용합니다. 같은 가구의 필드를 개별적으로 합치지는 않습니다. 서버에서 삭제됐지만 내가 수정한 가구가 복원될 수 있다는 점을 안내합니다. 저장 버튼을 아직 누르지 않은 구조도 재적용 대상입니다. 구조만 편집한 경우에도 새로고침 시 미저장 경고가 나옵니다.

구조와 가구의 복구는 별도 요청입니다. 구조 저장이 성공하고 가구 저장이 실패하면 성공한 구조의 버전을 다음 복구 기준으로 유지합니다. 구조 저장 자체가 실패하면 기존 편집 기준을 유지하므로 실행 취소가 미저장 구조를 저장된 것으로 오인하지 않습니다. 복구 도중 중복 클릭과 추가 편집은 잠시 막습니다.

제안 확인은 계속 `proposalId`만 보냅니다. 응답을 받지 못한 경우 같은 ID로 재확인할 수 있습니다. 재확인 결과의 구조가 달라졌다면 화면의 옛 구조와 서버의 새 버전을 섞지 않고 충돌 복구로 넘깁니다. 서버가 만료와 버전 충돌을 모두 409로 반환하므로 확인 요청의 409도 같은 복구 안내를 사용합니다. 사용자는 최신 내용을 확인한 다음 필요한 명령을 다시 요청해야 합니다.

실제 두 탭에서 가구 저장 충돌과 명시적 재적용 및 새로고침 후 보존을 확인했습니다. 모든 실패 경로를 실제 서버와 브라우저로 반복하는 자동 E2E와 CI 연결은 #11의 후속 작업입니다. 이 브랜치 검증은 main 반영이나 배포 완료를 의미하지 않습니다.

## 이행과 검증

`V9__integrate_project_revision.sql`은 V8까지 적용된 DB에 새 컬럼을 추가합니다. 프로젝트는 버전 0으로 시작합니다. 과거 제안의 기준 버전은 null로 남기며 현재 버전으로 채우지 않습니다. 그러면 오래된 제안이 잘못 유효해지는 것을 막을 수 있습니다.

이 경로는 기존 PR #80의 V6를 대체합니다. 이후 그 V6를 추가하면 같은 컬럼을 다시 만들거나 적용 순서가 어긋납니다. V6를 이미 적용한 별도 DB는 이번 업그레이드 지원 대상이 아닙니다. 먼저 실제 이력과 데이터를 확인하고 별도 이행 계획을 세워야 합니다. PR #78의 가구 카탈로그 V5도 현재 제안 저장 V5와 중복되므로 그대로 넣지 않습니다.

배포 시 구버전과 신버전 서버를 동시에 쓰기 가능 상태로 운영하지 않습니다. 구버전 서버는 revision을 증가시키지 않으므로 새 서버의 보호를 우회할 수 있습니다. 백업과 복원을 확인한 뒤 모든 쓰기를 멈추고 새 스키마와 서버를 적용합니다. 이전 서버로 단순 복귀하는 절차는 제공하지 않습니다. 문제가 생기면 쓰기를 멈추고 수정 배포 또는 검증된 복원을 선택합니다.

`./mvnw -Dtest=ProjectRevisionIntegrationTest test`는 실제 PostgreSQL과 MockMvc를 사용합니다. MockMvc는 네트워크 없이 HTTP 요청을 Spring 컨트롤러로 전달하는 테스트 도구입니다. 이 검사 통과는 실제 브라우저 E2E와 배포 및 여러 서버 인스턴스 운영 검증을 의미하지 않습니다.
