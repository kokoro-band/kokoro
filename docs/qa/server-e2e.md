# 실제 서버 브라우저 테스트

## 무엇을 확인하는가

#144는 #11의 첫 하위 작업입니다. E2E는 브라우저에서 시작한 행동이 실제 API와 DB 저장까지 이어지는지 확인하는 검사입니다. 기존 단위 테스트의 HTTP 대체 함수 대신 일회용 PostgreSQL과 Spring 서버를 사용합니다.

현재 자동화 범위는 다음과 같습니다.

| 시나리오 | 확인할 결과 |
|---|---|
| 새 프로젝트에서 빈 방을 만들고 의자 추가 | 새로고침 후 같은 프로젝트의 방과 가구 및 버전이 유지됩니다. |
| 같은 프로젝트를 두 탭에서 편집 | 두 번째 저장은 실제 409로 거절됩니다. 최신 확인만으로 서버는 바뀌지 않습니다. 재적용 후 두 탭의 가구가 같은 프로젝트에 남습니다. |

두 시나리오를 1280px과 390px 너비의 Chromium에서 각각 실행합니다. 좁은 화면 검사는 반응형 웹 검사이며 실제 휴대전화나 VR 헤드셋 검사가 아닙니다. 화면 프로젝트 이름과 정확한 프로젝트 조회 응답을 함께 비교하므로 기본 예제를 잘못 열어도 통과하지 않습니다.

## 실행 준비

Java 17과 Docker 및 Vite+가 필요합니다. Docker는 로컬 Unix 소켓으로 연결해야 합니다. 실행 전 프로젝트 파일 시스템과 임시 디렉터리에 각각 최소 1GiB의 여유 공간을 확인합니다. 첫 의존성 다운로드와 브라우저 설치 및 Docker 이미지 설치에는 추가 공간이 필요하므로 여유 공간을 충분히 확보하세요. 실행기는 공간을 확보하려고 기존 파일을 지우지 않습니다.

처음에는 프론트 폴더에서 다음 명령을 실행합니다.

```bash
vp install
vp exec playwright install chromium
```

Linux에서 브라우저의 시스템 라이브러리도 설치해야 하면 공식 안내에 따라 `vp exec playwright install --with-deps chromium`을 사용합니다. GitHub CI는 이 방식으로 준비합니다. 설치가 끝나면 다음 한 명령으로 DB 생성부터 서버 빌드와 웹 실행 및 테스트와 정리를 진행합니다.

```bash
vp run test:e2e
```

운영 URL이나 기존 DB 주소를 입력받지 않습니다. 실행기가 고른 로컬 포트만 사용합니다. 다른 실행과 포트 확보가 겹치면 자동으로 다른 서버를 재사용하지 않고 실패합니다. Windows 직접 실행은 지원하지 않습니다.

## 격리와 종료

실행마다 고유 이름의 DB 컨테이너를 만듭니다. 프로젝트는 테스트마다 화면에서 생성하고 해당 테스트가 만든 ID만 삭제합니다. 성공 여부와 상관없이 마지막에 자신의 라벨이 붙은 컨테이너를 종료합니다. 도면용 임시 폴더도 실행기가 만든 정확한 경로만 정리합니다. 사용자의 기존 DB와 업로드 폴더는 건드리지 않습니다.

자식 프로세스에는 실행에 필요한 기본 환경변수만 전달합니다. 외부 DB 주소와 Spring 설정 덮어쓰기 및 Java와 Node의 추가 실행 옵션을 전달하지 않습니다. Java 실행 인자로 로컬 보안 모드와 테스트 DB 및 업로드 폴더를 고정합니다. 따라서 이 검사는 운영 인증 완료의 증거가 아닙니다.

서버 준비에는 제한 시간이 있습니다. 서버가 먼저 종료되면 기다리기를 멈춥니다. 실행을 중단하면 소유한 프로세스 그룹에 종료 신호를 보내고 제한 시간 뒤에도 남은 자식은 강제 종료합니다. 실행기 부모가 먼저 종료돼도 하위 서버 추적을 유지합니다. 정리에 실패하면 성공으로 끝내지 않습니다.

## 실패 확인

테스트 재시도 횟수는 0입니다. 준비 완료나 UI 상태 및 HTTP 응답을 기다리며 고정 시간 대기로 테스트 순서를 맞추지 않습니다. 프로세스 준비 확인의 짧은 반복 조회는 UI 대기와 구분합니다.

프론트 폴더의 `.e2e-artifacts/`에 실행 로그가 남습니다. `playwright-report/`는 HTML 결과이며 `test-results/`에는 실패 화면과 브라우저 실행 기록이 남습니다. 실행 기록은 실패 지점의 UI와 요청을 되짚는 자료입니다. 테스트 데이터와 로컬 테스트 계정만 사용하고 실제 사용자 도면이나 운영 토큰을 넣지 마세요.

CI는 실패할 때만 세 폴더를 결과 파일로 올리고 7일 보관합니다. 실패 원인을 서버 기동과 환경 문제인지 또는 사용자가 기대한 동작의 실패인지 구분해서 기록합니다. 도구 미설치나 컴파일 실패는 TDD의 기능 실패 근거로 쓰지 않습니다.

## 남은 범위

방 분할과 합치기 및 문창 포인터 조절과 가구 이동 및 회전은 후속 브라우저 시나리오가 필요합니다. 업로드와 명령 확인 취소 및 응답 유실과 부분 복구 실패와 늦은 응답 및 프로젝트 전환도 #11에 남습니다. 기존 단위 테스트가 이 경계를 검사하더라도 실제 브라우저 자동화 완료로 표시하지 않습니다.

운영 인증은 #12에서 확인합니다. HTTPS와 헤드셋 및 발표 리허설 기록도 별도입니다. PR 검사 통과는 main 병합이나 배포를 뜻하지 않습니다.

설정 기준은 [Playwright의 CI 안내](https://playwright.dev/docs/ci-intro)와 [서버 준비 확인 안내](https://playwright.dev/docs/test-webserver)입니다. 이 저장소는 DB까지 정리해야 하므로 별도 실행기에서 서버 수명을 관리합니다.
