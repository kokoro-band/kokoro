# 실제 서버 브라우저 테스트

로컬 데모의 WebGPU 배치 요청은 [브라우저 AI E2E](local-ai-e2e.md)로 별도 실행합니다. 이 문서의 `test:e2e`는 실제 Spring 서버와 DB를 사용하는 검사입니다.

## 무엇을 확인하는가

#144는 #11의 첫 하위 작업입니다. E2E는 브라우저에서 시작한 행동이 실제 API와 DB 저장까지 이어지는지 확인하는 검사입니다. 기존 단위 테스트의 HTTP 대체 함수 대신 일회용 PostgreSQL과 Spring 서버를 사용합니다.

현재 자동화 범위는 다음과 같습니다.

| 시나리오 | 확인할 결과 |
|---|---|
| 새 프로젝트에서 빈 방을 만들고 의자 추가 | 새로고침 후 같은 프로젝트의 방과 가구 및 버전이 유지됩니다. |
| 같은 프로젝트를 두 탭에서 편집 | 두 번째 저장은 실제 409로 거절됩니다. 최신 확인만으로 서버는 바뀌지 않습니다. 재적용 후 두 탭의 가구가 같은 프로젝트에 남습니다. |

두 시나리오를 1280px과 390px 너비의 Chromium에서 각각 실행합니다. 좁은 화면 검사는 반응형 웹 검사이며 실제 휴대전화나 VR 헤드셋 검사가 아닙니다. 화면 프로젝트 이름과 정확한 프로젝트 조회 응답을 함께 비교하므로 기본 예제를 잘못 열어도 통과하지 않습니다.

## 실행 준비

Java 17과 Docker 및 Vite+가 필요합니다. Docker는 로컬 Unix 소켓으로 연결해야 합니다. 실행 전 프로젝트 파일 시스템과 임시 디렉터리에 각각 최소 1GiB의 여유 공간을 확인합니다. 첫 의존성 다운로드와 브라우저 설치 및 Docker 이미지 설치에는 추가 공간이 필요하므로 여유 공간을 충분히 확보하세요. 실행기는 공간을 확보하려고 기존 파일을 지우지 않습니다.

처음에는 프론트 폴더에서 다음 명령을 실행합니다.

```bash
vp install
vp exec playwright install chromium
```

Linux에서 브라우저의 시스템 라이브러리도 설치해야 하면 공식 안내에 따라 `vp exec playwright install --with-deps chromium`을 사용합니다. GitHub CI는 이 방식으로 준비합니다. 설치가 끝나면 다음 한 명령으로 DB 생성부터 서버 빌드와 웹 실행 및 테스트와 정리를 진행합니다.

```bash
vp run test:e2e
```

한 화면 크기만 확인할 때는 다음 중 하나를 실행합니다. 인자를 생략하면 두 화면 크기를 모두 검사합니다.

```bash
vp run test:e2e --project=desktop
vp run test:e2e --project=narrow
```

두 화면 선택 인자 중 하나를 허용합니다. 원본 업로드와 브라우저 이미지 분석 및 상태 조회 검사를 따로 확인하려면 `--suite=uploads`를 추가합니다.

```bash
vp run test:e2e --project=desktop --suite=uploads
vp run test:e2e --project=narrow --suite=uploads
```

이 선택자는 정해진 `uploads.spec.ts`만 실행합니다. 오타와 중복 선택 및 다른 Playwright 옵션은 Docker나 서버를 시작하기 전에 거절합니다. `--` 구분자나 `--project desktop` 형식은 받지 않습니다.

CI는 각 화면 크기에서 같은 명령을 두 번 실행하도록 설정합니다. `project: [desktop, narrow]`와 `repeat: [1, 2]`의 네 작업은 각각 자기 DB와 서버를 생성하고, 한 작업이 실패해도 다른 작업을 취소하지 않습니다. 실패 결과 이름에는 화면 크기와 반복 번호 및 실행 ID와 재실행 번호가 포함됩니다. 반복은 실패한 테스트의 자동 재시도와 구분합니다. 테스트별 60초 제한과 재시도 0회는 유지합니다. 검사 수가 늘어 전체 Playwright 명령의 한도는 15분, 서버 E2E CI 작업의 한도는 준비와 정리를 포함해 20분으로 둡니다. 로컬에서 같은 체크아웃의 두 검사를 동시에 실행하면 결과 폴더를 공유하므로 한 번에 하나씩 실행하세요.

#153의 분리 검증에서 브라우저를 실행하지 않고 테스트 목록을 비교했습니다. 전체 34개는 desktop 17개와 narrow 17개의 중복 없는 합과 일치했습니다. 이는 실행 대상 확인이며 실제 통과 여부는 각 CI 결과로 판단합니다. main 브랜치 보호 조회는 Branch not protected였고 저장소 ruleset 목록은 비어 있었습니다. 보호 설정을 변경하지 않았으며 이후 필수 검사를 설정할 때는 두 화면 작업 모두를 포함해야 합니다.

운영 URL이나 기존 DB 주소를 입력받지 않습니다. 실행기가 고른 로컬 포트만 사용합니다. 다른 실행과 포트 확보가 겹치면 자동으로 다른 서버를 재사용하지 않고 실패합니다. Windows 직접 실행은 지원하지 않습니다.

## 격리와 종료

실행마다 고유 이름의 DB 컨테이너를 만듭니다. 프로젝트는 테스트마다 화면에서 생성하고 해당 테스트가 만든 ID만 삭제합니다. 성공 여부와 상관없이 마지막에 자신의 라벨이 붙은 컨테이너를 종료합니다. 도면용 임시 폴더도 실행기가 만든 정확한 경로만 정리합니다. 사용자의 기존 DB와 업로드 폴더는 건드리지 않습니다.

자식 프로세스에는 실행에 필요한 기본 환경변수만 전달합니다. 외부 DB 주소와 Spring 설정 덮어쓰기 및 Java와 Node의 추가 실행 옵션을 전달하지 않습니다. Java 실행 인자로 로컬 보안 모드와 테스트 DB 및 업로드 폴더를 고정합니다. 따라서 이 검사는 운영 인증 완료의 증거가 아닙니다.

서버 준비에는 제한 시간이 있습니다. 서버가 먼저 종료되면 기다리기를 멈춥니다. 실행을 중단하면 소유한 프로세스 그룹에 종료 신호를 보내고 제한 시간 뒤에도 남은 자식은 강제 종료합니다. 실행기 부모가 먼저 종료돼도 하위 서버 추적을 유지합니다. 정리에 실패하면 성공으로 끝내지 않습니다.

## 실패 확인

테스트 재시도 횟수는 0입니다. 준비 완료나 UI 상태 및 HTTP 응답을 기다리며 고정 시간 대기로 테스트 순서를 맞추지 않습니다. 프로세스 준비 확인의 짧은 반복 조회는 UI 대기와 구분합니다.

프론트 폴더의 `.e2e-artifacts/`에 실행 로그가 남습니다. `playwright-report/`는 HTML 결과이며 `test-results/`에는 실패 화면과 브라우저 실행 기록이 남습니다. 실행 기록은 실패 지점의 UI와 요청을 되짚는 자료입니다. 테스트 데이터와 로컬 테스트 계정만 사용하고 실제 사용자 도면이나 운영 토큰을 넣지 마세요.

CI는 실패할 때만 세 폴더를 결과 파일로 올리고 7일 보관합니다. 실패 원인을 서버 기동과 환경 문제인지 또는 사용자가 기대한 동작의 실패인지 구분해서 기록합니다. 도구 미설치나 컴파일 실패는 TDD의 기능 실패 근거로 쓰지 않습니다.

SVG는 화면에 그려진 좌표를 읽어 실제 포인터 위치로 변환합니다. 앱 내부 상태나 Three.js 장면을 주입하지 않습니다. 캔버스 검사는 연속으로 같은 이미지가 나오는 상태를 기다립니다. 픽셀이 달라졌다는 사실만으로 정확한 문 회전 각도나 모델 품질 전체를 보장하지는 않습니다. 문 열림은 현재 화면의 일시적인 상태이며 저장 대상으로 가정하지 않습니다.

390px 검사는 마우스로 조작하는 반응형 화면 검사입니다. 실제 터치 입력과 모바일 기기 및 헤드셋 검증은 별도로 수행해야 합니다. 테스트당 60초 제한과 재시도 0회는 유지합니다. 이 편집 검사 추가 당시 전체 브라우저 명령의 한도는 10분이었으며, 현재 한도는 위 실행 안내를 따릅니다.

### 편집 검사에서 발견한 결함

첫 CI 실행은 14개 중 9개가 통과했습니다. 모바일 시트를 닫는 선택자가 여러 버튼과 일치한 문제와 벽에 붙은 의자가 15도 회전할 수 있다고 잘못 가정한 문제는 테스트 조건의 오류로 구분했습니다. 숫자의 소수 표현 오차와 잘못된 가구의 자동 위치 보정도 제품 결함으로 계산하지 않았습니다.

방을 분할하면 기존 외벽 창이 사라지는 현상은 실제 제품 결함이었습니다. 외벽을 구성하는 선분을 합치는 과정에서 방향이 바뀌면 벽 ID도 달라졌습니다. 기존 개구부가 사라진 벽에 붙어 있다고 판단해 제거한 것이 원인입니다. `fc022ea`의 단위 검사에서는 세로 분할과 가로 분할 모두 네 개의 외벽 창 중 세 개만 남아 실패했습니다.

첫 수정안은 개구부의 거리 값만 반전했지만 독립 리뷰에서 문 경첩이 반대쪽으로 이동한다는 문제가 확인됐습니다. 문 경첩과 열린 문 끝점의 실제 좌표 비교로 두 실패를 재현했습니다. 최종 수정은 기존 개구부가 참조하는 벽 방향 자체를 유지합니다. 새 속성이나 데이터 형식을 추가하지 않습니다. 사라진 내부 벽에 붙어 있던 개구부는 계속 제거합니다.

`326631d`에서 관련 기하 검사 73개와 전체 단위 검사 711개가 통과했습니다. `vp check`와 `vp run typecheck:e2e` 및 `vp run build`도 통과했습니다. 기존 큰 번들 경고는 남습니다. 이 기록은 로컬 검사 결과이며 최종 브라우저 통과 여부는 #148의 해당 커밋 CI를 별도로 확인해야 합니다.

후속 검사에서는 분할한 구조를 먼저 저장한 뒤 합쳐 저장할 변경을 만듭니다. 처음 구조로 되돌린 상태에서 비활성 저장 버튼을 누르려던 테스트 조건을 수정했습니다. 캔버스 캡처 때는 저장 알림과 떠 있는 도구막대만 숨겨 문 장면을 비교합니다. 모바일 시트는 닫힘 애니메이션 뒤 실제 요소가 제거될 때까지 기다린 다음 단축키를 보냅니다. 이 세 변경은 제품 수정이 아니라 검사 조건의 보정입니다.

최종 브라우저 검증은 `vp run test:e2e --project=desktop`의 30개가 4.1분, `vp run test:e2e --project=narrow`의 30개가 8.0분에 재시도 없이 통과했습니다. 각각 별도 체크아웃과 의존성 캐시 및 빌드 출력과 결과 폴더를 사용했고, 검사한 프론트와 백엔드 및 CI 코드 변경이 같은 것을 비교했습니다. 두 실행 모두 자체 Spring과 일회용 PostgreSQL을 정상 종료했습니다. 이는 총 60개 시나리오의 로컬 결과이며 CI 반복 실행 통과로 대신 표시하지 않습니다.

CI의 두 번 실행 설정은 구성 검증을 마쳤으며, 최종 커밋의 실제 CI 결과는 게시 후 별도로 기록해야 합니다.

첫 [CI 실행](https://github.com/kokoro-band/kokoro/actions/runs/38741027452)의 desktop 2회차에서 새 E2E의 전체 프로젝트 비교 10개가 실패했습니다. Java 쓰기 응답의 나노초 `updatedAt`과 PostgreSQL 조회의 마이크로초 반올림 값이 달랐고, 버전과 내용은 같았습니다. macOS 로컬 시계에서는 재현되지 않았던 테스트 비교 오류입니다. 저장 결과 비교는 나머지 필드를 모두 정확히 검사하고, 시간만 JavaScript 파서의 밀리초 경계 차이 1ms를 허용하도록 수정했습니다. 제품 응답이나 재시도 설정은 바꾸지 않았습니다. 수정 커밋의 네 독립 CI 실행을 새로 확인합니다.

운영 인증은 #12에서 확인합니다. HTTPS와 헤드셋 및 발표 리허설 기록도 별도입니다. PR 검사 통과는 main 병합이나 배포를 뜻하지 않습니다.

설정 기준은 [Playwright의 CI 안내](https://playwright.dev/docs/ci-intro)와 [서버 준비 확인 안내](https://playwright.dev/docs/test-webserver)입니다. 이 저장소는 DB까지 정리해야 하므로 별도 실행기에서 서버 수명을 관리합니다.
