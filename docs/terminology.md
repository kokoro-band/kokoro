# 개발 문서와 PR 용어

PR 제목과 본문 및 개발 문서는 아래 용어를 사용합니다. 프론트엔드 개발자가 해당 기능의 구현을 모르더라도 요청 흐름과 변경 이유를 이해할 수 있게 씁니다.

## 공통 용어

| 설명할 내용 | 사용할 용어 | 기존 표현 |
|---|---|---|
| API의 경로와 요청 및 응답 | API 명세 | API 계약 |
| JSON의 필드와 값의 구조 | 데이터 형식 | 데이터 계약 |
| 필드의 타입과 필수 여부를 검사하는 정의 | JSON 스키마 | JSON 계약 |
| 프론트엔드와 서버 또는 WebXR 사이의 동작 조건 | 연동 규칙 | 연동 계약 |
| 가구의 크기와 모델 파일의 기준 | 가구 규격 또는 에셋 규격 | 자산 계약 |
| 모델이 JSON으로 해석한 가구 작업 | 배치 요청 | 배치 의도 |
| 적용 전에 사용자에게 보여 주는 가구 변경 | 배치 제안 | 확인 제안 |
| 한 번 적용한 제안의 재사용을 막는 상태 변경 | 사용 완료 처리 | 제안 소비 |
| 캐시나 데이터를 읽는 동작 | 사용 또는 조회 | 데이터 소비 |
| 빌드로 생성한 dist 폴더나 JAR | 빌드 파일 | 빌드 산출물 |
| 실패한 테스트의 화면과 trace 및 로그 | 테스트 실패 기록 | 실패 산출물 |
| 작업을 시작하는 시점이나 순서 | 작업 시작 또는 작업 순서 | 착수 |

API 명세는 요청과 응답의 사용 방법을 설명합니다. JSON 스키마는 데이터 형식을 코드로 검사하는 정의입니다. 두 용어를 같은 뜻으로 섞어 쓰지 않습니다.

자연어 요청은 사용자가 입력한 문장입니다. 모델이 이 문장을 배치 요청 JSON으로 바꿉니다. 서버나 브라우저가 배치 요청을 검사하고 배치 제안을 만들면 사용자는 적용하거나 취소합니다.

## 작성 기준

- 주어와 행동을 적습니다. 예를 들어 "서버가 요청 형식을 검사하고 잘못된 값은 400으로 응답합니다"라고 씁니다.
- 한 문서나 PR에서 같은 대상을 다른 단어로 바꿔 부르지 않습니다.
- 표준 개발 용어는 유지합니다. DTO와 CORS 및 WebXR처럼 배경 지식이 필요한 용어는 처음 나올 때 뜻과 사용하는 이유를 설명합니다.
- 회귀 테스트는 기존 기능이 변경 후에도 동작하는지 확인하는 테스트입니다. RED는 구현 전 실패 테스트이고 GREEN은 수정 후 통과한 테스트입니다. 실제로 실행한 명령과 결과를 함께 적습니다.
- 문장을 다듬어도 테스트 개수와 실패 이유 및 미실행 항목을 바꾸지 않습니다. 로컬 검사와 CI 및 배포와 실제 헤드셋 확인은 각각 기록합니다.
- API 경로와 JSON 키 및 코드 식별자는 정확히 표기합니다. `docs/contracts/` 같은 기존 파일 경로도 그대로 사용합니다.

## PR 작성 전 확인

1. API와 데이터 형식 및 연동 동작을 공통 용어로 설명했는지 확인합니다.
2. 변경한 내용과 이유가 바로 읽히는지 확인합니다.
3. 검증 결과가 원문과 같고 실행하지 않은 항목도 남아 있는지 확인합니다.
